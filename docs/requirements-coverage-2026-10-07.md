## 结论和范围纠正

原始产品要求及用户认可的优化方案**尚未全部完成**。0.4 完成了一批可验证的可靠性基础；中央 Hub 远程接入、代码理解驱动的 PRD 分解、自动文件触发、完整可视化工作台、自动多轮治理和真实长期编码验收仍有缺口。

此前的工作主要针对虚假指标、数据一致性、生命周期和反馈隔离，没有逐条验收完整产品方案。尤其是把 UI 简化为列表/卡片、将接入限制为服务器本机目录、将 PRD 限定为离线候选，并不能视为用户取消原来认可的需求。原范围继续有效，这些当前限制应登记为未完成项。

## 保留的设计主线

应继续以“业务意图 → 代码范围与约束 → 人类审阅 → 工作区自动取上下文 → 编码过程中更新认知 → 需求结束提炼 → 可视化审计”作为产品目标。

已经完成的事务、版本、会话、反馈凭据等能力是这条链路的基础。当前 README 中的限制是交付状态说明，不能替代原产品范围。

不需要机械照搬的内容：

- Vue/React 或另一种 UI 实现是工程选型，验收应看交互能力与可靠性。
- P0/P1 条数必须来自真实需求，不能固定生成“3 条 P0 + 4 条 P1”。
- 反馈工具不能仅因名称带 RLHF 就声称已完成模型训练或自动提升质量。
- 完全相同作用域使用不同优先级可以合理，不应自动视为错误。

## 后续补齐顺序及验收边界

1. **办公机真实接入与触发**：远程 Hub 协议、客户端身份、`.codeneuro.json`、实际宿主适配。验收一个真实工作区和一个真实 coding agent 的自动文件上下文流程。
2. **需求与代码理解**：索引/实体关联、WebUI PRD 分解、可解释候选审核；避免用户手工把所有路径都补完。
3. **恢复完整可视工作台**：目录热力树/焦点视口、泳道、规则质量矩阵、工作区下发详情、快捷面板与实时事件。
4. **多轮治理闭环**：短期规则完整自治、失败反射、会话清理、任务提炼、建议采纳、静态 watch 同步。
5. **真实编码验收**：选择有明确验收条件的新需求，记录几十轮真实使用、改动和反馈；最后再进行完整产品验收。

以上排序是依赖关系建议，不代表把尚缺内容从需求中删除。
