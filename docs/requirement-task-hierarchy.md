# 需求、任务与上下文

CodeNeuro 采用一套当前模型和接口，不维护产品协议编号、数据库升级链或并行兼容层。本地存量数据通过一次性脚本转换。

## 业务层级

```text
Project
└─ Requirement：整体业务目标与整体验收要求
   ├─ Task：独立实现范围与验证要求
   └─ Task：独立实现范围与验证要求
```

例如“档号要素维护”是一项需求，“全宗号”“项目代码”“工程档案通用类目类号”可分别作为子任务。“全宗号不能重复”属于任务约束或规则，不额外拆成另一层需求。

每个 Task 必须属于同项目的一个 Requirement。没有 Atom Task、任意深度任务树，也不将聊天会话当成业务任务。

## 开发、验证和整体验收

| 对象 | 状态 | 含义 |
| --- | --- | --- |
| Requirement | draft | 整理目标，仅可添加待开始的子任务 |
| Requirement | active | 子任务正在推进，或整体验收未通过 |
| Requirement | accepting | 子任务全部验证完成，等待用户整体验收 |
| Requirement | completed | 用户明确确认整体验收通过，并填写验收结论 |
| Task | draft | 尚未开始 |
| Task | active | 实现中 |
| Task | testing | 开发完成，等待独立验证 |
| Task | paused | 暂停，保留暂停前状态 |
| Task | completed | 验证完成，已填写验证方式与结果 |

Task 从 testing 进入 completed 时必须提供 `verification_summary`。可选的 `verification_report_ids` 必须是本任务的成功报告；报告仅代表宿主上报，不声称 Hub 执行了测试。

所有未删除子任务验证完成，只会使父需求进入 accepting。用户确认整体验收后，Web 或获得用户授权的 Agent 才能提交 completed、`completion_summary` 和确认原因。空需求不能完成。验收未通过可以退回 active；已经完成的需求须先重开才能继续开发。

新增任务、重开任务、修改实现范围或验收要求会使已有验收准备失效。验证中的任务修改范围后退回 active；已完成任务须先重开。标题调整不抹掉验证结果。暂停恢复回到原来的 active 或 testing。

## 归档、删除与记录修订

归档用 `archived_at` 表示，是收纳状态，与开发完成无关。未完成的归档子任务仍阻断整体验收。恢复归档不改变业务状态。

删除用 `deleted_at` 表示，保留历史并撤回该工作范围，不代表已经完成；仍有子任务的需求不能直接删除。重开、恢复或删除都不会自动重新激活已停用规则。

记录的 `version` 用于防止并发覆盖和追溯正文修订，不是软件发行版本。更新和删除须携带当前 `expected_version` 与操作原因；旧修订快照和已签发 Delivery 不被覆盖。子任务改变时父需求修订号也会更新，防止在旧进度上确认整体验收。

## 直接定位工作范围

没有 start/end Session，也没有替代性的必建 run 或 conversation 句柄。

- 管理需求：显式 `project_id`。
- 创建子任务：显式 `project_id`、`requirement_id`。
- 读上下文：显式项目，可选 Task；传入 Task 时同时下发其父目标和本任务范围，不带入兄弟任务。
- 修改任务知识和上报验证：显式 `task_id`，校验记录属于这个任务。
- 不传 Task 的项目查询不从最近调用、工作区或来源推导任务。

另一位 Agent 可以继续同一个 Task；记录修订和证据归属约束仍然生效。可选 source/worktree 只是来源声明，不是身份认证、会话识别或默认任务选择器。

## 规则与下发

调用方显式选择 P0–P3；主题和真实相对文件至少提供一种。有主题时按主题判定适用性，文件只辅助排序；没有主题时按文件匹配。已选中且适用的 P0 完整保留，其余预算省略项明确返回。

下发保存实际正文、查询、规则/父需求/任务/Finding 引用与修订、匹配依据和省略信息。相同项目、操作和 request_id 的相同输入重放原结果；变更输入报冲突。新请求读取当前知识。按 Delivery ID 读取的是当时的快照。

反馈 0 分只表示“已知”，不会让下一位 Agent 缺失正文。评分和 Issue 不需要 debug 模式。Finding 是未审阅观察，不会自动变成 Rule。

任务完成后的短期规则可继续服务整体验收；整体需求完成、归档或删除相关范围时停用。规则验证仍按声明的检查和测试项绑定证据，同一次事件不能因更换 Agent、请求 ID 或时间区表示而重复计数。修改长期契约仍须审阅。

## 接口与工作台

MCP 和 HTTP 共享业务工作流。MCP 保留 20 个工具，参数和输出只对应当前模型；没有 Session 生命周期工具，也没有产品协议选择参数。每次返回一段 JSON 文本，正文不重复输出结构化章节。

需求和任务列表默认每页 20 条、最多 100 条，摘要超过 200 字符时标记截断。游标绑定资源、项目和筛选条件；详情提供完整文本，修订历史另行分页。账本统计来自数据库聚合，不用第一页长度冒充总数。

工作台按需求查看子任务、独立验证结果和整体进度。子任务详情、业务动作和修订历史分别展示；整体验收必须显式点击并填写结论。项目切换、异步加载和过期修订不会静默覆盖当前选择。

## 本地数据处理

新库直接初始化：

```sh
python -m codeneuro init-db --db /path/to/new.db
```

已有本地 Task/Session 数据用一次性脚本转到新文件：

```sh
python scripts/migrate_local_data.py \
  --source /path/to/old.db --target /path/to/new.db --mapping /path/to/mapping.json
```

脚本只读源库，拒绝覆盖已存在的目标。映射仅描述实际业务归属与状态，例如：

```json
{
  "requirements": [
    {"id": "archive-elements", "project_id": "archive", "title": "档号要素维护", "text": "整体业务目标"}
  ],
  "tasks": {
    "existing-task-id": {"requirement_id": "archive-elements", "status": "active"}
  }
}
```

示例 ID 必须换成实际记录；每个旧 Task 都明确指定父需求和新状态。旧归档或上线状态不自动视为验证完成。指定完成状态时，必须有相应验证或整体验收结论。

旧任务内的活跃条目并入该任务说明。原始条目、所有修订和规则/下发关联保存在任务导入记录中；旧 Delivery 原文和规则修订、反馈等实际记录保留。原库作为完整备份保存；不在新库复制一整套旧模型。历史快照作为当时记录读取，不重新解释成新父需求。

本地转换失败只清理本次新建目标。切换前停止旧服务写入，用已提交代码验证新库后再启动；需要退回时使用旧代码和保留的原库。如新库已经产生新数据，先保留这部分数据再决定处理方式。

批量导入另用 `scripts/load_batches_into_codeneuro.py`，输入直接包含 projects、requirements、tasks、topics、rules、findings，不需要格式编号。它只导入明确的初始业务记录，不承担历史转换，也不伪造验证结果。

## 验证范围

后端验证覆盖父子关系、独立验证、整体确认、归档/删除、并发修订、检索隔离、请求重放、规则证据、真实 stdio/HTTP MCP、数据库初始化与一次性转换。

浏览器使用临时库、独立回环服务和临时 Chromium 用户目录，验证需求创建、多个子任务、验证/验收、重开、修订历史、主题与规则治理。测试和构建结果以实际运行报告为准。
