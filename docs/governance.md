# 任务规则自治与长期契约审阅

治理、检索和优先级是独立维度。受控 Topic 与完整 v2 接口见 [主题升级契约](topics-v2.md)；Rule 无文件锚点不等于不能验证，P0 也不等于全局或免审阅。

## 任务草稿与验证计划

Agent 通过 `codeneuro_create_task_rule` 创建当前 Task 草稿，显式填写已登记主题和 `validation_spec`；草稿不进入 JIT。非全局规则必须有主题，`scope_patterns=[]` 合法，P0 要写后果/适用范围理由。

- `kind=test`：每条条款被检查覆盖，每个检查声明唯一 ID、条款索引（从 0 起）和宿主测试 ID。
- `kind=review`：填写规范依据，由人类审阅固定版本；人工审阅不能替代可测试规则的测试覆盖。

宿主实际运行测试后，以 `codeneuro_report_test` 上报 argv、可空的相关路径、退出码、带时区的起止时间和测试项的 passed/failed/skipped。CodeNeuro **只记录 client_reported**，不执行或保证真实性。Hub 接收时间用于阻止旧报告验证新语义，重复事件不能通过换请求 ID 伪造独立证据。

`codeneuro_observe_rule` 必须给出 `check_ids`，仅绑定当前规则证据版本中的声明检查。报告须覆盖计划中的测试 ID，而不是随意提交同 Task 的成功命令；失败或跳过项不能作为支持。整体及每个检查都满足两份不同成功证据、无反证、有效置信度至少 0.6，才允许 Agent 激活测试规则。

规范草稿通过 `POST /api/projects/{project_id}/rules/{rule_id}/review` 提交人类批准/拒绝、预期版本和理由。所有审阅保留版本依据。

标题、条款、主题、路径、全局声明、验证计划改变或优先级升级，使规则增加版本、退回草稿并重置证据；降级优先级和状态变更不声称旧测试验证了新条款。Topic 只改显示名不会修改 Rule 版本或使证据失效。

## 晋升与长期契约

`codeneuro_promote_rule` 仅原样复制当前 Task 活跃短期规则的条款、主题、范围、等级、全局声明和验证依据；不借此扩大适用范围。源规则失活，来源版本及审计同事务保存。

`codeneuro_propose_contract` 引用目标长期规则及 Task 候选的固定 ID/版本，不再接受任意替换文本。可测试候选先验证激活，规范候选接受人类提案审阅。批准时重新检查目标/候选版本、项目/任务、状态、关联需求和证据；漂移则冲突，不自动合并。批准后应用候选语义并停用候选。旧 v1 提案不可直接批准，须重新提出；拒绝入口仍可用于结束旧提案。

## 主题维护与存量切换

Topic key 稳定、删除后不复用；首次被知识引用后冻结业务边界。活跃/草稿 Rule、待审阅 Finding、未决 Proposal 阻断删除，不能强删或级联摘除。知识重新分类必须使用各自的版本治理入口；Finding 可显式重分类或结束，未决提案可人类拒绝。

迁移不会猜测主题或伪造证据。未分类旧规则由人类通过 `/rules/{id}/classify` 固定版本、确认真实业务范围和规范依据；已有验证计划的规则不能走此迁移入口绕过正常治理。活跃规则（尤其 P0）和未审阅 Finding 分类完成后，由人类按目录修订开启项目主题查询。

## 完成需求与反馈

`codeneuro_archive_requirement` 由 Agent 确认实际完成并提交摘要，Hub 不核验代码或执行测试。关联短期规则随需求归档失活；最后一条活跃需求归档完成 Task 并停用其余短期规则。暂停或已发布状态须先按既有状态流程处理。

`score=0` 仅表示本会话该版本已知，不降低优先级或价值；已经被等级数组选中且适用的 P0 保留全文。评分和 Issue 仍要求真实下发凭据与 `debug=True`。所有状态变化、版本、来源和审计同事务提交；Web 与 MCP 共用工作流。服务没有鉴权，不能声称验证了人类身份。
