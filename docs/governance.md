# 规则治理

优先级、业务适用性和验证方式分别表达不同信息。Topic 定义见[主题与查询](topics.md)，任务生命周期见[需求与任务](requirement-task-hierarchy.md)。

## 创建与验证

Task Rule 归属于一个明确 Task，初始为 draft，另一位 Agent 可以接续操作。非全局规则使用已登记主题；scope_patterns 可以为空。P0 需要说明严重损害与适用边界，不能借优先级扩大业务范围。

可测试规则给出 validation_spec：

```json
{"kind":"test","checks":[{"id":"invalidate-pointer","clause_indexes":[0],"test_ids":["VolumeRevisionIT#invalidate"]}]}
```

每条条款必须被检查覆盖。宿主报告明确列出 test_id 与 passed/failed/skipped；observe_rule 提供 check_ids，将本 Task 的实际报告绑定到当前规则修订。报告必须在相关修订之后产生，测试项必须覆盖声明检查；路径只用于检索，不充当验证证据。

激活需每项检查获得两次独立成功事件、没有反证，并满足有效置信度至少 0.6 的既有约束。同事件更换请求 ID、Agent、路径排序、测试项排序或等价时间区表示，不增加证据次数。Hub 只记录客户端结果，不执行或认证测试。

无法测试的规范使用 `{"kind":"review","basis":"明确规范依据"}`，由人工入口审阅固定草稿修订。人工按钮不能代替可测试规则的证据。

## 修订、晋升和长期契约

语义内容、主题、范围、验证计划或优先级升级会重置候选证据并退回草稿；普通显示名修改与规则内容修订区分处理。修改提交 expected_version 与 reason，拒绝静默覆盖。

晋升引用当前活跃 Task Rule 的确切修订，原样复制条款、主题、路径、全局声明、等级和验证依据；不扩大范围，保留来源并停用原候选。

修改已有长期契约须提交目标与 Task 候选的固定 ID/修订。可测试候选先完成验证；规范候选接受人工提案审阅。批准时再次检查双方修订、状态、归属和证据；发生变化就报冲突，不自动合并。缺少候选或验证依据的提案需要重新提交。

Task 单独完成后，短期规则可继续用于父需求整体验收；父需求整体完成、归档或删除相应范围时停用。恢复或重开不会自动激活这些规则。

## 观察、反馈与冲突

Finding 是 Task 范围的未审阅观察，可显式重新分类或解决，不自动晋升。评分需要真实 Delivery 和规则引用：0 表示已知，1–5 表示效用，0 不计入效用均分，也不降低优先级或隐藏后续正文。

Issue 不要求 debug。冲突报告需 Task 和至少两条不同规则，记录当时修订，但仍是待处理报告，不声称 Hub 已完成裁决。

状态、修订、来源和审计同事务提交；Web 与 MCP 共用用例。产品无鉴权，human 和 actor 仅为来源标签，不能证明真实用户身份。
